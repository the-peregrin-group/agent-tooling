# Proposal: Stream doc

## Draft entry

**Stream doc**: A document that records events in the order they happened
(e.g., a chat log, a work log, a decision log), whose value is the record
itself; it grows by appending, and an existing entry changes only to make
the record clearer or truer, never to hide or alter what happened.
- _Invariants_: entries are diffs (what was learned, decided, or done on a
  date), never a restatement of current state; an entry contains nothing
  learned after its date; the current state of anything is never derivable
  only by replaying a Stream doc

## Relationships

- A State doc may embed one bounded Stream doc section at its end; a Stream
  that is unbounded or large lives in its own document, referenced from the
  State doc.
- A TODO list is a Stream doc section: an open item is a future event, a
  closed one a past event; it tracks a plan the State doc's sections define.

## Naming questions

1. Why a term: the counterpart of State doc; the `refine-state-doc` Skill and
   the Documentation rules in `CLAUDE.md` rely on the pair. No industry term
   fits: "log" and "journal" are everyday words that imply a particular form
   (a log file, a diary) rather than the editing discipline.
2. Core identity: an append-only record of events whose provenance is the
   point.
3. Candidates: Stream doc (chosen: pairs with State doc, and the
   `refine-state-doc` Skill already uses it), Log (rejected: everyday word,
   implies a file format), Journal (rejected: everyday word, implies a
   diary).
4. Collisions: none with an entry, an Avoid word, or a retired term.
