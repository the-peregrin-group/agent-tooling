# Proposal: State doc

## Draft entry

**State doc**: A document that describes one entity (e.g., a design, a plan,
a project's status) as it is at one point in time, by default now, and that is
updated by rewriting its body in place so it always reads as one coherent
picture rather than as a sequence of edits.
- _Invariants_: one owning place per fact, with every other mention a
  reference to it; readable end to end without replaying its history; a
  State doc anchored at a past date states that date in its header and is
  never updated to describe later state

## Relationships

- A State doc may embed one bounded Stream doc section (a TODO list, a
  decision log) at its end; that section owns events, the rest owns facts.
- A design doc is a State doc, living or anchored at a date.
- Under `docs/projects/`, `index.md` and `design.md` are living State docs;
  every other doc there is a State doc anchored at its date.

## Naming questions

1. Why a term: the `refine-state-doc` Skill and the Documentation rules in
   `CLAUDE.md` turn on the distinction, because it decides how a document is
   edited (rewrite in place versus append). No industry term fits: "living
   document" covers only the point-in-time-is-now case, and "snapshot"
   suggests a copy of something else.
2. Core identity: one coherent picture of an entity at a fixed point in time,
   maintained by rewriting.
3. Candidates: State doc (chosen: the `refine-state-doc` Skill already uses
   it, and the name says what the doc holds), Living doc (rejected: excludes
   docs anchored at a date), Snapshot (rejected: implies a copy).
4. Collisions: none with an entry, an Avoid word, or a retired term. The
   Status table in `docs/projects/*/index.md` has a column named `State`
   (the closed set `shipped`, `planned`, `proposed`, `retired`), an everyday
   use of the word, not this term.
